# 5.2.1 本地数据架构

## 权威数据与版本

结构化数据和二进制文件均以 IndexedDB 为权威存储。沿用 `qicheng-v4` 数据库名，数据库结构版本升为 2；可编辑 HTML 副本仍按副本 ID 使用独立数据库。数据库结构版本、`current.modelVersion`、应用版本及外部备份版本各自独立，不能用清理程序缓存来“升级数据库”。

采用原生 IndexedDB，保留一个 `records` 对象仓库。对象仓库的字符串主键本身是有序索引；`IDBKeyRange.bound(prefix,prefix+'\uffff')` 提供按命名空间的 B-tree 有界查询，不需要把所有记录读入内存再筛选。`getPrefixPage` 可限制读取数量及方向。

| 键 | 内容及关联 |
| --- | --- |
| `current` | 工作区字段清单、稳定记录 ID 顺序、模型版本；不含图片正文 |
| `@521:ws:<字段>` | 个人资料、设置、草稿等小对象或标量 |
| `@521:ws:<集合>:<ID>` | 荣誉、经历、院校收藏关系、自我介绍、简历版本、附件元数据等独立记录；集合顺序保存在清单 |
| `@521:ws:learning.books:<ID>` | 阅读经历独立记录，阅读文本与经历分离 |
| `@521:blob:<不可变文件引用>` | 原始附件 Blob，保留原始字节和 MIME 类型 |
| `@521:thumb:<不可变文件引用>` | 预览缩略图 Blob，最长边 320 像素；元数据保存小型预览数据 URL 供同步模板使用 |
| `@521:bank:meta:...` / `@521:bank:q:...` | 题库元数据及永久 ID 题目，与个人作答记录独立 |
| `quiz:*`、`journal:*`、`home:*` 等 | 各业务的独立状态和历史；通过统一存储接口提交 |
| `@521:rev:<键>`、`@521:clock` | 数据库事务内递增的并发版本，内部数据不进入外部备份 |

新数组记录有唯一 ID 时按单条拆分；空数组和不适合 ID 拆分的轻量值保存为字段行。已有业务模型与同步模板保持投影兼容，避免改变现有导出、编辑、照片关联语义。当前工作区的文字元数据仍会一次读入；附件原文、题库正文、历史详情和大型静态资源由调用方按需读取。这是明确的兼容边界，并非所有模块都已改为完全按页读取。

## 读写接口和迁移

`getCurrent({lazyAssets:true})` 在同一个只读事务中读取清单、元数据行和工作区版本，避免跨标签页产生混合快照。返回有效缩略图和受信任的内部文件引用，普通附件仅返回空数据 URL 占位。`validateDraft(...,{trustedLocal:true})` 仅用于本机投影；从外部文件恢复时禁止内部引用，必须有完整原始附件数据。

`get('current')`、`getAll()` 返回可恢复的完整旧模型投影，附件原始字节转为数据 URL，题库内部行恢复为公共题库记录。`getAll()` 是只读导出快照，绝不刷新正在编辑的乐观并发版本。`materializeCurrent(snapshot)` 用于将当前编辑快照转换为完整备份数据；`assetBlob`、`assetData`、`photoData` 仅在下载、查看原图、裁剪或导出时读取原始附件。

数据库升级本身只打开原对象仓库，不在 `onupgradeneeded` 中大量解码照片。5.2.0 的完整 `current` 仍可直接读取，第一次成功保存时才原子拆分为字段、记录、附件 Blob。失败会保留原有完整记录；未发生任何编辑时不会为迁移强制重写所有数据。旧版尚未升级的代码在结构版本 2 数据库上不能继续以版本 1 打开，从而避免旧代码覆盖新版模型。

## 自动保存与并发

自动保存保留 500 毫秒防抖及现有失焦/页面切换提交时机。保存队列串行执行；每次保存从元数据生成快照，已提交附件及照片关联的 Base64 在克隆之前被排除，指纹也不序列化原图。数据库只 `put` 真正变化的行，普通点击和重复保存不会产生数据写入。

每项记录都有事务内生成的递增版本。`setMany` 可显式传入 `expected`；一般读写接口会保存本窗口读取的基准。自动保存额外固定 `ctx.workspaceRevision521`，仅在启动、恢复或成功提交后更新，避免备份、调试读取等操作把旧 UI 的版本基准误推进。即使只修改一个字段，工作区版本也随实际提交递增。

两个标签页编辑同一工作区时，后提交的旧副本抛出 `StorageConflictError`，保留内存中的编辑并提示先外部备份、再重新载入；不会静默覆盖先提交的数据。目前采用保守冲突拒绝，尚不提供跨标签页逐字段交互合并。`update` 的同步回调与写入处于同一个读写事务，保留具体错误原因。

本地保存状态仅在 `transaction.oncomplete` 后显示成功。事务失败、配额不足会保留待保存状态并提示；关闭页面不是唯一保存机会。恢复使用先完整校验、再准备 Blob、最后一次事务替换的流程；事务失败时原库完整回滚。

删除附件或替换文件引用时，旧元数据中已不再被新快照引用的原始 Blob 和缩略图在同一提交中回收。照片只关联 `assetId`，移除某个照片关联不会删除仍留在素材库的原始文件。备份的 `getAll()` 从同一只读事务读取所有原文，避免与附件回收交错产生半份快照。

## 技术选择和边界

本轮不采用 OPFS：IndexedDB Blob 已提供事务、同库关联和跨 Chromium 平台支持；目前没有实测证据证明额外文件系统、清理索引和跨存储提交会有净收益。未来确有大体积文件瓶颈再基于此数据接口扩展。OPFS 同样受浏览器站点存储管理，不能作为浏览器之外的独立备份。

Cache Storage 仅管理程序资源；LocalStorage 不保存重要个人数据。设备普通文件系统由用户主动保存备份。持久存储申请降低自动驱逐风险，但不能抵御主动清站点数据、浏览器配置文件丢失或设备故障，必须保留外部完整备份。

## 实际验证

- `node --experimental-vm-modules --test tests/storage521.test.mjs tests/autosave521.test.mjs`：10 项通过，覆盖只更新变化行、原始字节投影、并发拒绝、备份后仍拒绝旧编辑、配额失败回滚、恢复失败回滚、更新回调错误、附件垃圾回收、无效重复保存和排队保存。
- `node tests/storage521-browser.mjs`：Windows 上实际 Edge、独立临时配置，验证 768×1024 原图精确恢复、240×320 缩略图、4 MiB 附件精确恢复、懒加载附件占位、单字段写入、独立标签页冲突、刷新后保留数据。原始证据保存在 `tests/generated/storage521/evidence.json`。测试需要允许启动本地 Edge。
- 该专项脚本的单次单字段提交约 1.7 毫秒，仅是本机小场景记录，不能单独作为相对于 5.2.0 的性能提升结论。完整性能对比以总验收报告为准。Android Edge 真机、长期浏览器驱逐、物理设备故障均未据此宣称测试通过。
