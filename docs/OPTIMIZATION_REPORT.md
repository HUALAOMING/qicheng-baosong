# 5.2.1 再次优化：文件按需打开与题库导入加速

日期：2026-10-29。本轮在 qicheng-5.2.1-optimized 中交付，保留上轮 qicheng-5.2.1 不改动，未上传、发布或部署。

## 结论与实际原因

上一轮变慢确实与新架构的实现方式有关，但不是稳定架构必然要付出的全部代价。原先通用存储接口会对已经预检和比较过的每道题再 get 旧值、get 修订号、JSON 比较、put 新题与 put 单题修订号。5000 题首次导入实际产生 10008 次 get、10006 次 put。读取现有题库时，还对每行读取单题修订号；一次重复导入或补丁预检产生约5000次多余 get。分块校验每200题用 setTimeout(0) 让步，也受到嵌套计时器的最短延迟影响。图片上传则会解码原图、绘制 canvas 并生成缩略图。

## 改动与保留的保护

1. 不再生成任何缩略图。文件/图片中心及资料选择器仅显示文件名、类型、大小等元数据，没有 img，也不读取原图。点击“打开”才从 IndexedDB 读取原始 Blob：图片按原分辨率显示，小型文本按纯文本显示；其他类型提供原文件保存并用设备应用打开。关闭预览释放 Object URL。已有头像、记录照片在相应页面打开时读取原件；裁剪和成果导出仍保留。
2. 旧缩略图不参与加载或显示；下次成功保存工作台时在同一事务里移除可再生的缩略图并清理旧预览元数据，不删除原件。失败则回滚，不在后台强制重写用户全库。
3. 已由题库业务层计算过的增量使用专用批量提交：事务内核对题库整体修订号以及目录修订号，随后直接写实际变化题目，不重复读取每题旧值或维护每题额外修订记录。首次5000题实际为6次 get、5006次 put。仍是一次 strict 事务，不拆成可能部分成功的分段提交。
4. 题库行由题库修订号整体保护；全库读取前后检查该修订号，取消无用的逐题修订读取。同一会话已加载的题目仅在数据库修订未变时复用。预检计划继续固定修订号，确认期间别的窗口修改仍拒绝提交。一般个人资料、草稿与学习标记仍走原有独立并发保护，不采用题库批量捷径。
5. 分块验证保留真实计数，优先使用 scheduler.yield()，回退 MessageChannel，最后才用计时器。不是删除校验、取消事务或关闭严格持久化换取速度。题目永久 ID、字段补丁、完整备份、旧数据兼容、作答快照和失败回滚均保留。

题库的所有业务写入必须继续通过题库仓库及其修订标记；不得让新业务直接修改内部题目行而不更新题库修订。此约定是专用批量接口安全高效的前提。初次迁移旧整包资源仍使用原有保守迁移流程，不冒险为了本轮导入优化修改恢复和迁移协议。

## 实测

Windows 实际 Edge，无头模式、本地 HTTP。对上轮5.2.1和本轮各使用3个独立浏览器上下文；每轮5000道唯一ID判断题，统计完整预检与实际事务完成，不含用户确认等待、系统文件选择器或首次安装程序资源。重复/补丁紧随初次导入，属于已加载题库的同一会话。中位数如下，不能外推为所有设备的固定耗时。

| 操作 | 上轮5.2.1 | 本轮优化版 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 首次完整导入 | 562.8 ms | 175.4 ms | 68.8% |
| 同一会话重复导入 | 694.6 ms | 40.9 ms | 94.1% |
| 同一会话单题解析补丁 | 686.6 ms | 49.8 ms | 92.7% |

重复导入仍为零 put。本轮单题解析补丁5次 get、5次 put；预检内容和未指定字段保留。图片实测每轮上传一个768×1024 PNG，旧版触发一次缩略图解码，本轮为0次；文件中心图片节点0个，点击打开后原图宽高仍为768×1024。完整原始数据、各阶段耗时和数据库请求数量见 OPTIMIZATION_PERFORMANCE_RAW.json，复跑命令 `node tests/optimization-browser.mjs`，需要相邻的旧工程作对照及本机 Edge/Playwright 路径。

仍有成本：逐题存储必须写入5000行，比5.2.0的单条整包写入请求更多；并不承诺回到5.2.0整包写入的耗时。补丁预检仍校验合并后的题库，首次打开未加载题库也需读取数据。本轮消除重复开销，保留可维护性与数据保护。
